# Public contracts and consistency

Target architectural shapes, not implemented endpoints or final OpenAPI. Retain same-origin `/api/v1` and [ADR-0001](decisions/0001-modular-monolith-boundaries.md), [ADR-0002](decisions/0002-owned-persistence-and-history.md), [ADR-0004](decisions/0004-resource-authorization.md). Changes under [ADR-0008](decisions/0008-approved-requirement-impact.md) are Proposed.

## HTTP and compatibility

Use explicit DTOs, server validation, pagination/size limits and errors with `code`, safe Polish `message`, `correlationId` and optional field errors. Codes distinguish invalid input (400), unauthenticated (401), forbidden or consistently concealed resource (403/404), state/revision/idempotency conflict (409), unmet policy (422), throttling (429) and transient failure (503). Choose a consistent inaccessible-resource response before publishing each API.

Money is a decimal string plus currency, restricted to PLN purchases in MVP. Significant times are ISO instants/offsets. Distinguish preliminary/review/final results, purchased/active participation, and pending/uncertain/successful refunds. Exclude persistence entities, provider payloads, unnecessary child data and pre-review answer keys.

Compatibility is additive within v1; breaking fields/state semantics require a new API/event version and migration. Existing contracts are unimplemented, so removal of proposed retake-entitlement shapes needs no deployed-client migration. Each implemented slice must supply exact schemas, bounds, status meanings and contract tests. Cookie-session CSRF/cookie details remain subject to ADR-0006; verified provider webhook routes use provider authentication separately.

## Authority and concurrency

Every query/command receives verified actor or narrowly scoped service context, with original actor/event evidence for audit. IDs in a request never establish authority. Resource owners recheck active guardian relation, teacher assignment, enrollment/access period, grants and required MFA. Workflows composes these checks and cannot bypass them.

Mutating contracts accept expected aggregate revision and a stable request key when retries can duplicate effects. Same key and same request return the recorded outcome; changed payload under the same key conflicts. Transactional ownership and request/result storage remain with the capability, not workflows. Expiry, quota, capacity and remaining refund amount are server-calculated.

## Payment delivery and refund recovery

Internal envelope: eventId, eventType, schemaVersion, occurredAt, producer, aggregateId, aggregateRevision, correlationId and minimal typed payload. Producer owns claim/ack/retry persistence; consumers never query its tables. Handlers are explicitly wired in workflows; no broker, dynamic event framework or event-sourced domain is introduced.

PaymentConfirmed v1 belongs to commerce and references orderId, paymentId, orderLineIds, decimal settled amount and PLN. Workflow resolves authoritative snapshots/state through PaidOrder; provider payloads do not escape infrastructure.

1. Adapter verifies authenticity, merchant/payment/order identity, amount/currency and authoritative state. Network verification occurs outside the local transaction.
2. Commerce locks state, commits unique callback/payment transition and delivery intent atomically; acknowledge provider only after commit.
3. Workflow uses one local transaction to resolve original-seat capacity, record one order-line enrollment effect or an explicit paid/unresolved resolution case, enqueue notification intent and mark delivery consumed. Unresolved means payment handling is durable, not successful enrollment; a separate owner-controlled resolution can retry capacity or execute recorded alternative/refund.
4. Crash before commit rolls back all local effects; retry after commit cannot duplicate them. Notification delivery remains independent.
5. Accepted alternatives revalidate target capacity and record guardian acceptance and original-order lineage atomically. Full refund is the resolution when original service cannot start and no accepted alternative is used; no silent transfer.
6. Refund intent and reserved balance commit before provider dispatch. Stable provider keys, callback deduplication and reconciliation protect repeats/crashes/uncertain responses. A submitted request is not a successful refund. Successful provider evidence atomically settles the reserved amount and audit/delivery status; definitive failure releases it. Do not retry an uncertain non-idempotent operation blindly.

Separate provider events for the same payment still produce one transition and order-line effect. Refund/service-change coordination never silently deletes attendance, attempts or purchased history. Safe outbound retries follow NFR-010; exact interval semantics/tolerances remain SA-Q-009 before operational acceptance.
